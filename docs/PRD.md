# 호기야 PRD

복성초등학교 6학년 2반의 수업 후 선진단과 맞춤 복습을 돕는 웹앱 「호기야」의 제품 요구사항 문서입니다. 무엇을 왜 만드는지를 정하고, 기능별 동작은 [SPEC.md](./SPEC.md)에서 정합니다. 용어는 [CONTEXT.md](../CONTEXT.md)를 따르고, 구조에 영향을 준 결정은 [docs/adr/](./adr/)에 있습니다.

## 1. 문제

- 학생 20명이 국어·영어·수학·과학을 과목별 교사에게 배우므로, 한 과목 교사는 다른 과목에서 학생이 어디서 막히는지 알 수 없습니다.
- 교사가 수업 직후 개념별 이해를 확인하려면 손으로 채점하고 모아야 하고, 다음 수업 전에 끝내기 어렵습니다.
- 학생은 자기가 무엇을 헷갈렸는지 모른 채 다음 수업으로 넘어갑니다.

## 2. 현재 운영의 한계

| 한계 | 결과 |
|---|---|
| 수업 후 확인이 구두 질문이나 활동지에 머묾 | 일부 학생만 파악되고 개념별 기록이 남지 않음 |
| 채점 기준이 교사의 머릿속에 있음 | 같은 답을 두고 판단이 달라지고, 근거를 되짚을 수 없음 |
| 복습 안내가 학급 전체에 같음 | 이미 아는 학생과 헷갈린 학생이 같은 복습을 함 |

## 3. 사용자와 의사결정 흐름

| 주체 | 입력 | 판단 기준 | 결과 |
|---|---|---|---|
| 교사 | 수업 자료, 선진단 5문항, 루브릭, 확인 활동 안내 | 문항이 5개이고 개념과 루브릭이 갖춰졌는가 | 수업 공개 |
| 학생 | 선진단 답안 | 루브릭 | 개념별 이해 수준과 복습 안내 |
| 학생 | 복습 중 질문 | 현재 개념과 승인된 수업 자료 | 호기의 근거 있는 설명 |
| 교사 | 학급 대시보드 | 최근 시도 기준 수준 분포 | 다음 수업에서 다시 다룰 개념 결정 |

예외와 승인은 아래와 같습니다.
- 호기의 진단과 추천은 참고 정보이고, 보충지도 여부는 교사가 정합니다.
- 호기가 근거를 찾지 못하면 추측하지 않고 자료 확인이나 교사 질문을 안내합니다.
- 교사는 자기 과목의 수업과 답안만 열 수 있습니다.

## 4. 범위

**첫 버전에 포함**
- 교사·학생 웹 화면, 모의 데이터 기반(1주차)
- 수업 자료와 선진단 5문항, 루브릭 등록과 공개
- 선진단 제출, 개념별 이해 수준, 복습 화면
- 호기 패널의 모의 응답
- 교사 대시보드(합성 데이터 집계)

**첫 버전에서 제외**
- 성장 기록(재진단에 따른 변화 추이)
- 실제 NEIS 성적 연동, 실제 학생 정보
- 파일 업로드형 수업 자료
- 서술형 이유 문장의 자동 판정

**주차별 계획**

| 주차 | 내용 | 해당 요구사항 |
|---|---|---|
| 1 | 화면과 모의 데이터 | FR-01~06, 08 |
| 2 | 호기 패널에 MCP와 Claude API 연결 | FR-06 실연결, FR-07 |
| 3 | Supabase, RLS, 합성 데이터, 대시보드 실연결 | FR-01·08 실연결, FR-09 |
| 4~5 | 교사 채점 사례로 평가와 개선 비교 | FR-10 |

## 5. 핵심 Entity

학급, 학생, 교사, 담당 배정, 수업, 수업 자료, 문항 세트, 문항, 루브릭, 개념, 시도, 이해 수준, 확인 활동 안내. 정의는 CONTEXT.md가 정본입니다. 관계의 핵심은 아래 세 가지입니다.
- 수업은 학급과 과목에 속하고, 교사는 담당 배정으로 그 범위만 엽니다.
- 문항 세트는 수업에 연결되고 공개 뒤 수정하면 새 버전이 됩니다(ADR 0001).
- 시도는 학생과 문항 세트 버전에 연결되고, 집계는 학생별 최근 시도 기준입니다(ADR 0002).

## 6. 기능 요구사항

| ID | 요구사항 | Spec |
|---|---|---|
| FR-01 | 학급·과목별 교사 권한 | S01 |
| FR-02 | 수업 자료 등록 | S02 |
| FR-03 | 문항 세트와 루브릭 등록, 공개 | S03 |
| FR-04 | 학생의 선진단 제출 | S04 |
| FR-05 | 이해 수준 판정과 맞춤 복습 | S05 |
| FR-06 | 호기 패널 | S06 |
| FR-07 | 승인된 교육 자료 조회(MCP) | 2주차 Spec에서 작성 |
| FR-08 | 교사 학습 대시보드 | S07 |
| FR-09 | 정보 최소 수집과 기록 삭제 | 3주차 Spec에서 작성(1주차에도 실명 입력 칸을 두지 않음) |
| FR-10 | 평가 실행과 개선 비교 | 4주차 Spec에서 작성 |

## 7. AI·자동화 기회

- **1주차**: 자동화는 규칙 함수 하나입니다. 선택형 답안과 루브릭으로 개념별 수준을 정합니다.
- **2주차**: 호기 패널의 응답 함수를 Claude API 호출로 바꿉니다. 교체 자리는 한 곳입니다.
- **후속**: 이유 문장의 판정, 맞춤 확인 활동의 생성, 성장 기록입니다. 데이터 표준화와 루브릭이 먼저 안정돼야 가능합니다.

## 8. 성공 기준

| 지표 | 기준 |
|---|---|
| 교사가 수업을 공개하기까지 | 자료, 5문항, 루브릭 입력을 한 화면 흐름에서 끝냄 |
| 학생의 선진단부터 복습 확인까지 | 한 번의 흐름으로 끝나고 중간에 길을 잃지 않음 |
| 교사가 다시 다룰 개념을 찾는 일 | 대시보드의 첫 화면에서 재지도 대상 개념이 보임 |
| 권한 위반 | 다른 과목 답안 요청과 타 학생 답안 요청이 모두 거절됨 |
| 중복 요청 | 같은 시도 키를 다시 보내도 시도가 늘지 않음 |

## 9. 리스크와 Trade-off

| 리스크 | 대응 |
|---|---|
| 문항과 오개념 예시가 교사 검수 전 초안임 | 화면에 "검수 전 초안" 표시를 두고 검수 후 교체 |
| 규칙 판정은 선택형만 평가하고, 이유 문장은 평가하지 못함 | 이유 문장은 저장과 교사 열람까지만 하고 2주차 이후 호기에 위임 |
| 실제 AI 없이 만든 호기 패널은 진짜 호기와 다르게 보일 수 있음 | 모의 응답임을 화면에 표시하고, 응답 함수를 한 곳에 둠 |
| 공개 후 수정으로 버전이 늘어나면 집계 화면이 복잡해짐 | 집계에 버전을 표시하고, 첫 버전은 최신 버전 기준으로만 보여 줌 |
| 실제 학생 정보 유입 | 입력 칸에 실명과 연락처를 두지 않고 합성 ID만 사용 |

## 10. 가정

| 가정 | 확인 시점 |
|---|---|
| 5문항 중 이유 문장을 쓰는 문항은 교사가 문항마다 정하며, 이유 문장은 선택 입력임 | S03 검토 시 |
| 한 수업은 문항 세트 하나를 가짐 | S03 검토 시 |
| 마감한 수업도 마감 전 시도의 결과와 복습은 계속 볼 수 있음 | S02 검토 시 |
| 학급은 6학년 2반 하나뿐이며 학급 선택 화면은 만들지 않음 | S01 검토 시 |
